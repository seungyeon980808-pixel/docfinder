# DocFinder 반응성 개선 및 로컬 검증 — 2026-10-10

## 기준과 범위

- 수정 전: 이 프로젝트의 `ba74bb7b5aa5e6a5b1a801ab1a1c0bad6bb196e3`를 Git archive로 별도 복원한 코드. 수정 후: 현재 작업 코드. 공유 측정 JSON의 `sources` SHA-256 5개를 각각 기준 커밋·작업 파일과 대조했다.
- 참고는 5E의 작업 폴더가 아니라 Git 태그 `v1.6.2` (`c086f36bf286c722f12763475e041847661a42b7`)와 `v1.6.3` (`3427fb5e6804b19259fd2fbe06f7b1ad2bba1945`)의 지정 파일이다. `catalog-startup.js`는 1.6.3에서 추가되었으며, 두 태그의 thumbnail queue 및 목록 갱신 방식을 함께 읽었다.
- 5E의 선표시·지연 준비·작업 큐·상태 보존·세대 검사 방식을 DocFinder의 Node/PGlite, 검색 Worker, PDF.js/RHWP 구조에 맞게 적용했다. **이 보고서의 모든 측정치는 DocFinder에서 새로 측정했으며 5E 성과 수치를 사용하지 않았다.**
- 운영 서버·Google 설정 변경·배포·커밋·푸시는 수행하지 않았다.

## 측정한 지연 원인과 수정

1. 공유 목록과 파일 이름 검색이 전체 쪽 본문을 불러오는 corpus 생성에 연결되어 있었다. 목록·건수는 SQL 메타데이터 조회로 분리하고, 본문 색인 준비는 목록 표시 후 실행한다. 파일 이름 검색은 이미 받은 목록에서 즉시 처리한다. 실제 로컬에서는 최초 화면 후 유휴 시점에 Worker를 준비해 초기 조작과의 경쟁을 줄였다.
2. 같은 파일을 다시 선택하거나 검색어를 바꿀 때 원문을 중복 요청했다. 현재 탭의 48MiB·8개 캐시, 요청 공유, 원문 동시 작업 2개, 전체 검색 corpus 준비 1개로 제한한다. 공유 캐시 재사용 때에도 HEAD로 권한과 최신 버전을 확인한다. 계정·문서함 변경이나 권한 회수 때 이전 자료를 재사용하지 않는다.
3. PDF 첫 쪽이 원래 해상도의 렌더링을 기다렸다. 640px 미리보기 후 기존 DPR 해상도를 별도 캔버스에 렌더링해 교체한다. 원본 다운로드·편집 데이터는 변경하지 않는다. 한글은 기존 벡터 원문과 편집기를 유지하며 중복 로딩·작업 큐를 개선했다.
4. 목록 재생성과 원문 버전 갱신이 입력·포커스·읽던 위치를 잃게 했다. 동일 목록은 선택만 갱신하고, 새 버전은 같은 파일일 때 쪽·쪽 내부 위치·선택한 검색 위치를 이어받는다. IME 입력, 열린 편집기 확대와 미저장 편집 내용을 유지한다.
5. 늦은 응답이 현재 파일·검색을 덮어쓸 수 있었다. 검색 순번, Worker 세대, 문서함/원본 버전, AbortController 검사를 추가했다. 새 응답이어도 권한과 버전이 이미 바뀌었으면 적용하지 않는다.
6. 자료 준비 실패와 아직 색인 중인 문서를 구분하기 어려웠다. 준비 중·완료·실패·재시도 상태를 표시하며, 실패 후 자동 무한 재시도를 하지 않는다. 아직 새 파일 색인이 진행 중이면 준비 완료로 표시하지 않는다.

## 반복 측정 방법

- 같은 컴퓨터, Node v26.8.1, Playwright Chromium, 1280×800, DPR 2에서 각 버전·조건별 5회씩 수행했다. 수정 전 실행을 마친 뒤 수정 후를 실행했고 성능 측정 중 다른 QA를 실행하지 않았다.
- 최초 방문은 새 브라우저 context이며, 공유 조건은 서버의 corpus·메타데이터 캐시도 비운다. 재방문은 같은 context를 새로고침해 준비된 서버 corpus와 정적 리소스를 재사용한다. OS 전체 파일 캐시를 지우거나 컴퓨터를 재부팅한 측정은 아니다.
- **첫 표시**: 페이지 이동 시작부터 문서 목록이 생긴 뒤 두 animation frame을 지난 시점. MutationObserver가 브라우저 안에서 기록한다. 실제 사용자 화면의 물리적 픽셀 표시를 측정한 것은 아니며 두 프레임 기준의 표시 지표이다.
- **실제 조작 가능 시간**: 이동 시작부터 자동화의 실제 클릭이 문서 선택(`aria-current`)에 반영되고 두 프레임을 지난 시점. 파일 선택이 실제 성공한 시간이며, 모든 본문 색인·원문 해상도·편집기 로딩 완료 시간을 뜻하지 않는다. 조작 시도에는 자동화 클릭 준비 시간이 포함되지만 두 버전에 동일하게 적용했다.
- 파일 이름 검색은 trusted input 시작부터 한 개 결과가 표시된 뒤 두 프레임을 지난 시간을 기록했다. 입력 시작은 capture 단계에서 기록하여 즉시 검색의 DOM 변경보다 먼저 측정한다.
- 목록 확인용 자동화 polling 시간이 섞였던 초기 결과는 `diagnostics/`로 옮기고 성과 계산에서 제외했다. 아래 네 JSON은 수정한 같은 측정 스크립트로 재측정한 최종 결과다. 최종 5회 표본 중 제외한 값은 없다.
- 중앙값과 P95를 함께 기록했다. 표본이 5개이므로 여기서 P95는 해당 5회 중 최댓값이다. 작은 차이의 통계적 유의성을 주장하지 않는다.

### 공유 문서함의 느린 데이터 의존성 재현

실제 DocFinder 서버·PGlite·PDF.js를 실행하되 테스트 자료만 사용했다. PDF 16개 × 24쪽, 본문 6,220,800자, 각 원문 7,144바이트. API마다 150ms, 전체 corpus DB 읽기에 600ms, 원문 의존성에 1,000ms를 동일하게 주입했다. 실제 Google/Render의 현재 지연을 측정한 결과가 아니다.

| 방문 | 지표 | 수정 전 중앙값 / P95 | 수정 후 중앙값 / P95 | 중앙값 변화 |
|---|---|---:|---:|---:|
| 최초 | 첫 표시 | 1134.5 / 1174.7ms | 930.3 / 957.3ms | -18.0% |
| 최초 | 파일 선택 반영 | 1195.3 / 1238.6ms | 980.8 / 1002.8ms | -17.9% |
| 최초 | 파일 이름 검색 반영 | 352.1 / 356.0ms | 14.5 / 14.8ms | -95.9% |
| 재방문 | 첫 표시 | 499.7 / 505.9ms | 507.5 / 515.5ms | +1.6% |
| 재방문 | 파일 선택 반영 | 539.4 / 547.3ms | 547.9 / 555.2ms | +1.6% |
| 재방문 | 파일 이름 검색 반영 | 356.1 / 356.7ms | 14.6 / 15.5ms | -95.9% |

첫 방문의 목록과 선택은 개선되었고, 재방문의 목록·선택은 약 0.5초 수준으로 유지되며 소폭 증가했다. 파일 이름 검색은 두 방문 모두 개선되었다. 모든 조건의 첫 표시가 빨라졌다고 주장하지 않는다.

A→B→A 선택·검색 초기화 시나리오에서 원문 의존성 읽기는 매 방문 6회에서 2회로 줄었고, 관측 최대 동시 작업은 3개에서 1개로 줄었다. 최초 방문마다 전체 corpus는 1회, 재방문은 0회로 두 버전 모두 동일하다. 수정 후에도 본문 검색 준비를 생략한 것이 아니다.

원문 첫 표시와 원래 해상도 완료 시간은 공유 JSON의 `originalDisplayMs`, 수정 후 `originalQualityDisplayMs`에 별도로 보관한다. 전자는 가벼운 미리보기일 수 있으므로 원래 품질 준비 시간으로 해석하지 않는다. 두 주요 지표(목록·파일 선택)의 개선과 원문 품질 검증을 구분한다.

### 실제 연결 폴더 15개 문서

같은 연결 폴더와 준비된 색인으로 수정 전 localhost:4181, 수정 후 localhost:4173에서 측정했다. 서버와 문서 자료는 같은 컴퓨터에 있으며 지연을 주입하지 않았다. 문서 수·시간만 기록하고 개인 문서 이름·본문은 측정 자료에 저장하지 않았다.

## 남은 확인 범위

운영 배포는 하지 않았다. 실제 운영의 네트워크, 동시 접속, Google 응답, 서버 요금제 영향은 이번 로컬 재현 측정에서 확인되지 않았으며 배포 지시 후 별도로 측정해야 한다. 자료를 브라우저에서 편하게 탐색할 수 있는 시점과 원래 해상도·전체 색인이 모두 준비된 시점은 별개로 표시한다.
